### Journey Tracker

##### Author: Kai

##### Installation

simply clone the repository and run JourneyTrackerApp.java

admin panel password = "meow"

###### Class Rider:

- unique ID
- name
- passenger type
- default payment option
  (can be created, saved and loaded as a JSON file)

###### Admin:

- is able to view/add/update/delete the configuration file, including:
- base fare (by zones and peak)
- passenger discount
- daily cap
- peak time window
  The admin menu is protected with a password (perhaps password can also be changed through the configuration file).
  Any updates made by the admin require validation.

###### Storage:

- permanent storage is saved either as a CSV or JSON
- JSON: configuration file, profile
- CSV: journeys, reports (alternatively could output a second report file as a .txt file)
- profiles (JSON), journeys (CSV) and the configuration (JSON) file can be loaded by the program.
- reports (CSV or .txt) are produced for the user to view

possible functionality: program is able to create reports as 2 files: one is a readable text summary, the other one is a
csv file.

###### System:

- on launch must load a configuration file, if not present then system must start with safe default values (perhaps
  automatically create a configuration file and plant it with default values)
- base fare is applied by zones and peak, and then discounts are applied
- each passenger type should not exceed the daily cap for that type
- should read/write JSON and CSV
- validation: when invalid values are entered the values should not be saved and the user should get a clear feedback
  message
- on exit menu must offer to save the rider’s current day state (consists of profile(JSON) + journeys(CSV))

###### Journey:

- unique ID
- date/time
- from Zone
- to Zone
- time band (peak/off-peak) (perhaps calculated automatically based on the time of creation of journey and the peak time
  window set by the admin)
- passenger type
- zones crossed
- base fare
- discount applied
- charged fare
- caps applied
- rider ID
  (can be imported from and exported as a CSV file)

###### Summary should have:

- number of journeys
- total cost
- average cost per journey
- most expensive journey (by charged fare) and its ID
- whether daily cap was reached and what were the savings compared to uncapped fees
- category counts: peak vs off-peak, counts per zone
  (summary should be exported as a CSV report with line items (each row shows the amount of money spent on a specific
  type of journey) and human-readable text summary saved in the report that includes date and rider name)

###### Welcome menu:

+++ Welcome to CityRide! +++
Please choose from the following:

1. New rider
2. Load rider
3. Admin panel

###### Rider:

###### 1. New rider/1. Edit profile - will make the user enter the following details:

1. Name
2. Passenger type (choosing 1-4 respectively to the offered passenger types)
3. Default payment option (choosing between offered payment options, for example "rail card" or "visa bank card")

After the new rider was created/Rider profile details were updated, a Rider menu is shown:

###### Rider menu:

1. Edit profile (takes the user to 1. New rider/1. Edit profile)
2. Load journeys
3. Add journey
4. List journeys
5. View (daily) summaries
6. Remove journey
7. Reset day
8. Save
9. Export summary
10. Exit (will prompt the user to save profile and journeys before exiting)

###### 2. Loading journey:

attempts to read a CSV file with journeys (possibly asks the user to input the file name without the extension), if file
is not present or contains invalid data should output a corresponding message to the user

###### 3. Adding journey:

take input from the user:

- date (validate the date, or the system could assign it automatically)
- starting & destination zone (validate that each zone is a number that corresponds to the existing zones, from 1 to 5)
- passenger type (validate that user chose a type that exists)
- time band (peak/off peak)
  journey is then stored in memory with the following fields:
- journey ID (a unique ID generated by the system automatically when the journey is created)
- date/time (entered or system assigned)
- is peak (flag to indicate the timeband)
- zones crossed (alternatively could store the start & destination zone, and then calculate zones crossed when
  outputted, or store both values without calculating)
- passenger type (Adult, Student, Child, Senior Citizen)
- base fare (always calculate)
- discounted fare (calculate if applicable, depends on the passenger type)
- charged fare after applying daily cap to the running total for that passenger type (calculate if applicable)
- daily cap reached (a flag to show if daily cap was reached)

###### 4. Remove journey:

take input from the user:

- journey ID (validate that the ID exists, an error message otherwise)
  the program then:
- asks for confirmation from the user
- removes journey from the memory
- recalculates totals and daily cap for the affected passenger type

###### 5. List journeys menu:

1. List all journeys (no filters)
2. List journeys with filters
3. Save all journeys

the program outputs the journeys in the order they were initially entered by the user, with all of the fields that were
stored in the process of adding the journey (journey ID, date, start zone & destination zone, time band, passenger type,
zones crossed, base fare, discount applied, charged fare after the applying daily cap). the user can choose to apply
filters or list journeys without the filters.
the journeys can be filtered by:

- passenger type
- time band
- zone (from or to)
- date
  the program will give the option to save the list of all journeys as a CSV file.

###### 6. View daily summaries:

the user can view summaries for:

- total number of journeys (all types)
- total costs charged (sum across all types)
- average cost per journey
- most expensive journey with its ID
- totals by passenger type:
    - journey count
    - pre-discount count
    - discounted sum
    - charged sum after daily cap & if cap was reached & what were the savings compared to uncapped fees
- category count:
    - count of peak vs off peak
    - count per zone pair or per each zone involved
      program should give an option to export the summary as a report

###### 7. Reset day:

the program:

- asks user for confirmation
- clears all journey
- clears all running daily totals and daily caps for each passenger type

###### 8. Exit:

- asks the user if they would like to save current day state (profile and journeys), if so then saves them
- exists the program

###### 9. Save:

- attempts to save current profile (JSON) and journeys (CSV)
- outputs clear feedback message to the user

###### 10. Export summary

- creates a CSV file containing summary report as well as a human-readable text summary (potentially could be its own
  .txt file)

###### Admin menu:

after choosing "3. Admin panel", the user is prompted to enter the admin password, if the entered password was correct,
the program shows admin panel that can manage system rules:

###### 3. Admin panel:

1. View rules
2. Edit rules*
3. Exit

the changes made by the admin affect the JSON configuration file and are validated before being saved. Upon passing
validation, the new journeys added by riders will follow the new configuration file rules.
No need for a separate option to add rules as it is functionally identical to editing rules since the config file will
start with default values.

No need for a separate option to delete rules as the program will ask the user to leave filed blank if they wish to
delete the rule.

###### 1. View rules

the admin will be able to view rules:

- peak time window (start hour, end jour)

- discount rates

- daily caps

- base fares (from zone, to zone, timeband : money)

###### 2. Edit rules

the admin will be able to edit (for each passenger type):

- peak time window (one for all passenger types)

- passenger discount

- daily cap

- base fare (by zones, timeband)

when the field is left blank, the admin deletes the current rule, and instead, a default value is loaded by the program
into the config file.
